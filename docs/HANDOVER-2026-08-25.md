給接手的人。這份說明 2026-08-25 這天做了什麼、東西跑在哪裡、怎麼維運、以及踩過哪些坑。

## 一句話總結

原本的服務沒有辦法知道「哪一位同仁生成了什麼」，紀錄也只留 14 天且每次部署就清空。這次加上 Clerk 公司帳號登入、把每次生成的完整內容（含圖片）永久歸檔、做了一個後台可以逐筆回查，並把服務部署到自架主機上，分成 staging 與 production 兩套。

## 1. 程式改了什麼

### 新增檔案

| 檔案 | 用途 |
|---|---|
| `clerk_auth.py` | 驗證 Clerk session token（本機用 JWKS 驗章，不是每次打 Clerk API），再以 Backend API 補 email／姓名並快取一小時 |
| `audit_archive.py` | 每次生成寫一份 metadata JSON + 圖片到磁碟，按月分目錄，**不自動清除** |
| `admin_console.py` | `/admin` 列表頁，可按月份與使用者篩選、直接看圖 |
| `static/auth-bootstrap.js` | 前端登入引導。`index.html` 與 `hybrid.html` 共用 |

### 修改檔案

- **`main.py`**
  - `clerk_login_gate` middleware：設了 `CLERK_PUBLISHABLE_KEY` 才啟用，並接手 `SITE_PASSWORD` 的角色
  - `verify_internal_api_key`：除了原本的 `X-API-Key`，也接受有效的 Clerk Bearer 權杖
  - `_archive_generation()`：把三個生成端點的歸檔收斂成一支，身分注入只寫一次
  - `_remember_digest()` / `_recall_digest()`：補回新聞原文（見下方「已知限制」）
  - `/auth-config.json`：公開端點，讓前端知道要用哪個 Clerk 實例
- **`entrypoint.sh`**：啟用 Clerk 時**跳過**把金鑰 sed 進 `app.js` 的動作（重要，見「踩過的坑」）
- **`index.html` / `hybrid.html`**：載入 `static/auth-bootstrap.js`
- **`pyproject.toml` / `uv.lock`**：新增 `pyjwt[crypto]`

### 設計原則

**所有新功能都是「設了對應環境變數才啟用」**，不設就完全是舊行為。這讓原作者的本機開發與既有部署完全不受影響。

`app.js`（一萬多行、7 個 fetch 呼叫點）**完全沒有改**。權杖是靠 `auth-bootstrap.js` 包一層 `window.fetch` 自動附加的，對前端主檔透明。

## 2. 部署在哪裡

服務跑在 AI 部門的自架主機上（Ubuntu 24.04），**不經過 Zeabur**，用 systemd 管理，對外走 Cloudflare Tunnel。

| | staging | production |
|---|---|---|
| 對外網址 | https://aicg.tvbs.dev | https://aicg.tvbs.ai |
| 後台 | `/admin` | `/admin` |
| 目錄 | `~/apps/aicg-champion-daihsuan` | `~/apps/aicg-prod` |
| 埠 | 8080 | 8081 |
| **分支** | `feat/clerk-audit-log` | **`release`** |
| systemd | `aicg.service` | `aicg-prod.service` |
| 稽核歸檔 | `~/aicg-audit` | `~/aicg-audit-prod` |
| Clerk | dev 實例 `stable-mackerel-35` | 正式實例 `clerk.tvbs.ai` |
| OpenRouter 金鑰 | 各自一把，分開計費 | 各自一把 |
| 後台密碼 | 各自一組，不通用（已實測） | 各自一組 |

隧道 `aicg-box1` 一條服務兩個網址，不需要建第二條。

**東京的 Zeabur 版本（`aicg-daihsuan.zeabur.app`）沒有被動過**，`main` 分支也維持原狀。

### 為什麼不用 Zeabur

主機一度掛成 Zeabur 的 Wonder Mesh 節點，也成功部署過，**但拿不到對外網址**——Wonder Mesh 的服務必須透過 gateway 才能對外，而 gateway 得跑在另一台有公網 IP 的專屬伺服器上。三次實測都被擋：

```
綁 .zeabur.app 網址 → WONDER_MESH_SERVER_REQUIRES_GATEWAY
綁自訂網域          → WONDER_MESH_SERVER_REQUIRES_GATEWAY
開 TCP 埠轉發       → 設定成功但主機上不會出現 NodePort
```

現有的專屬伺服器都載著其他團隊的服務，決定不動，改用 Cloudflare Tunnel。附帶好處：不經 Zeabur 就不需要掛 volume，稽核檔直接寫主機硬碟。

## 3. 環境變數

**金鑰不在 repo 裡，也不在本文裡。** 實際值在主機上的 `~/apps/<目錄>/.env`（權限 600）。

| 變數 | 說明 |
|---|---|
| `PORT` | staging 8080 / production 8081 |
| `OPENROUTER_API_KEY` | 兩套用不同金鑰，帳單分得開 |
| `CLERK_PUBLISHABLE_KEY` | 公開值。程式會從它反解出 Clerk 網域，不必另設 |
| `CLERK_SECRET_KEY` | 機密。與 publishable **必須同一實例**，混用會出現「登不進去但沒有明顯錯誤」 |
| `ADMIN_PASSWORD` | 後台密碼。**不設就完全不掛載 `/admin`（404）** |
| `AUDIT_ARCHIVE_DIR` | 稽核歸檔目錄。不設就不歸檔 |
| `REQUEST_LOG_RETENTION_DAYS` | 設為 36500（100 年）。**原始預設是 14 天** |
| `ALLOWED_EMAIL_DOMAINS` | 選用。逗號分隔的允許網域。**目前刻意不設**，見下方說明 |

### ⚠️ `NEWS_IMAGE_API_KEY` 請保持不設定

啟用 Clerk 之後前端拿不到也不需要這把金鑰。而 `verify_internal_api_key` 是拿 `X-API-Key` 跟它比對的——**只要它有值，任何人送出那個值就能通過驗證**。留空時程式 fail-closed，才是安全的。

（2026-08-25 曾把它設成佔位符 `REPLACE_ME`，等於公開的通行碼。已移除。）

### `ALLOWED_EMAIL_DOMAINS` 為什麼寫了卻不啟用

Clerk 的 allowlist 需要 Pro 方案，而且是「整個實例」層級——`clerk.tvbs.ai` 是共用正式實例（330 位使用者，不只本專案），改它會牽動其他 TVBS 服務。所以在自家後端做了一份。

但實測確認現有 SSO 已經夠嚴密（見下節），所以**目前不啟用**。留著是為了：共用實例的登入設定若被其他團隊改動，加一個環境變數即可立刻補上，不必改程式。

## 4. 登入與存取控制

### 誰進得來（2026-08-25 實測）

```
password / email_address / phone_number / username : 全部 off
Google OAuth    : 同意畫面為 Internal → 個人 Gmail 得到 403 org_internal
Microsoft OAuth : 僅公司/學校帳號 → 個人 Hotmail 被明確拒絕
SAML / enterprise_sso : disabled
```

**只有公司帳號進得來。** `clerk.tvbs.ai` 已有 330 位 TVBS 內部使用者，同事不需要重新註冊。

### 判斷 OAuth 有沒有限定組織：只能用真帳號實測

這點吃過虧，記下來：

- ❌ 看 authorize 網址是不是 `/common/`——那只代表**入口**接受兩種帳號，真正的關卡是 Azure 應用程式註冊的受眾設定，從外部看不到
- ❌ 拿 client_id 打 `/consumers/` 端點看有沒有 AADSTS 錯誤——會成功載入 `login.live.com`（HTTP 200、無錯誤），但那只是畫面外殼，受眾檢查發生在**輸入帳號之後**
- ✅ **用真的個人帳號在登入畫面實際跑一次。** 被擋會有明確訊息。在 staging 測，不要用 production

### 三道門的分工

| 路徑 | 誰在把關 |
|---|---|
| `/`、`/hybrid.html`、`/auth-config.json`、`/static/` | 公開（不公開的話使用者連登入畫面都載不出來，會變成死結） |
| `/app.js`、`/hybrid.js` | 公開，但啟用 Clerk 時**不含金鑰**（只有佔位符） |
| `/api/*` | Clerk 登入 |
| `/admin` | 獨立的 `ADMIN_PASSWORD`（同仁知道站台怎麼進，但後台看得到所有人的產出） |
| `/line/`、`/static/generated/` | LINE webhook 走自己的 HMAC 驗簽 |

## 5. 維運

### 更新程式碼

主機上**沒有 GitHub 認證**（刻意的，不把 token 放主機），所以不能 `git pull`：

```bash
# 在自己的電腦上
git clone --depth 1 -b <分支> https://github.com/TVBS-AI/aicg-champion-daihsuan.git /tmp/src
rsync -az --delete --exclude '.git' --exclude '.venv' --exclude '__pycache__' \
  --exclude 'logs/' --exclude 'static/generated/' --exclude '.env' --exclude '.env.bak*' \
  /tmp/src/ <主機>:~/apps/<目錄>/
ssh <主機> 'export PATH=$HOME/.local/bin:$PATH; cd ~/apps/<目錄> && uv sync --frozen --no-dev'
ssh <主機> 'systemctl --user restart <服務>.service'
```

**`--exclude '.env'` 不能少**，否則會洗掉主機上的環境變數。

### 常用指令

```bash
systemctl --user status  aicg.service aicg-prod.service cloudflared-aicg.service
systemctl --user restart aicg-prod.service
journalctl --user -u aicg-prod.service -n 50
```

三個服務都設了 `Restart=always`，且已 `loginctl enable-linger`，重開機會自動啟動。

## 6. 踩過的坑（重要）

### 1. `entrypoint.sh` 會就地改 `app.js`，曾因此外洩金鑰

`entrypoint.sh` 在服務啟動時把 `__NEWS_IMAGE_API_KEY__` 佔位符 **sed 成真實金鑰、直接改磁碟上的檔案**。

當時為了修「`app.js` 被登入門 401 擋住」而把該檔改為公開，並在 `main.py` 的 `_serve_js_with_key()` 加了「啟用 Clerk 就不代換」的防護——**該防護無效**，因為 sed 早在啟動時就完成了，讀檔時佔位符根本不存在。金鑰在公開網址上暴露約 4 分鐘。

**教訓：防護要加在真正動手的那一段，不是加在下游讀取的地方。** 正解是 `entrypoint.sh` 在 `CLERK_PUBLISHABLE_KEY` 有值時整段跳過 sed。

### 2. Clerk 的 `__session` cookie 帶不到 `<script src>` 請求

原本把 `/app.js` 擋在登入門後、想靠 cookie 驗身分。實測登入成功後 app.js 仍一路 401，**症狀是「頁面打得開但所有按鈕沒反應」**（app.js 沒載入，介面是空殼）。

判讀關鍵：log 裡**沒有** `[clerk_auth] token rejected`，代表後端根本沒收到權杖，而非驗證失敗。

正解是把防線從檔案移到 API：app.js 公開但不含金鑰，`verify_internal_api_key` 改收 Clerk Bearer 權杖。

### 3. `entrypoint.sh` 在 repo 裡沒有執行權限

Dockerfile 靠 `RUN chmod +x` 補。rsync 會把 644 同步過來，systemd 直接 `203/EXEC` 起不來。
systemd 單元固定寫 `ExecStart=/bin/sh .../entrypoint.sh`，不依賴執行位元。

### 4. `/healthz` 回 404 是正常的

`main.py` 把 `/healthz` 列進豁免清單卻從未定義該路由。回 404（而非 401）反而證明豁免有效。**健康檢查請改用「首頁回 200」。**

### 5. Cloudflare `cloudflared tunnel login` 會失敗

該流程要簽發帳號層級憑證，撞權限牆：`Failed common permission check against resources. (Permission group: "Load Balancing: Monitors and Pools Write")`

改從 Zero Trust 後台建立隧道、取得連接器權杖，用 `--token-file` 跑。

另外 `tvbs.ai` 的 DNS 紀錄需要 admin 權限；一般成員建路由時 DNS 那步會失敗但介面仍顯示成功。

### 6. DNS 負快取會讓人誤判「沒生效」

紀錄加好之後，本機與公司 DNS 可能還記著先前的 NXDOMAIN（TTL 1800 秒）。判斷方式：

```bash
dig +norecurse @ashton.ns.cloudflare.com <網域> A      # 問權威伺服器
curl --resolve <網域>:443:<IP> https://<網域>/          # 繞過本機解析
```

## 7. 已知限制與待辦

1. **新聞原文是「使用者＋時間窗」關聯補上的，不是嚴格關聯。** 前端把「消化」與「生圖」拆成兩次獨立請求，生圖端點只收到 prompt（`news_text` 原本就寫死成 `""`）。後端記住每位使用者最近一次消化的原文（TTL 30 分鐘）再補回去。同一人短時間內換稿再生圖，補上的是最近一次消化的原文。要嚴格關聯得改 `app.js` 的呼叫參數與後端 request model。

2. **`/healthz` 路由仍未定義**（見坑 4）。加一個回 `{"ok":true}` 的路由是小改動，值得做。

3. **CORS 仍是 `allow_origins=["*"]`**（`main.py`），建議收斂成自家網域。

4. **LINE bot 沒有動過**，webhook 仍指向東京的 Zeabur 版本。

5. **同機不同環境不是真正的隔離。** staging 與 production 跑在同一台實體機器上，斷電或硬碟故障會兩套一起死。若此工具成為新聞部日常依賴，正式環境應搬到有機房保障的地方。

6. **`clerk.tvbs.ai` 是共用實例。** 其他團隊調整登入設定會影響本服務且不會有人通知。真的發生時，設定 `ALLOWED_EMAIL_DOMAINS` 即可自保。
