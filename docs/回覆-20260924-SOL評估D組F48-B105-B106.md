## 2. B105：「字少」與「字極少」擠在一起

### 現行契約對照

兩角色共用 density block；差別主要來自編輯基礎樣板的 150–180 字、每行 15 字、三行範例（`main.py:1463-1482`）。

| 檔位 | 記者版 | 編輯版額外影響 | 點數／每點／標題 | 程式硬守門 |
|---|---|---|---|---|
| 無字 | variable 必須空 | 同左 | 0／0／0 | 空 variable 僅此檔放行，`main.py:2855-2872` |
| 不改字 | 原文逐字、原長度 | 明文覆蓋編輯上限 | 原文／不限／不限，`main.py:1834-1845` | token 上限 24K，`main.py:397-426`；另有不完整逐字 gate |
| 字極少 | 先套字少，再要求 ONE point | 編輯三點範例會形成反向錨點 | 1 點；每點約 ≤12；標題 ≤10，`main.py:1623-1632` | **無點數或字數硬守門** |

另有全域失控上限 40 行（`main.py:2734-2741,2900-2905`），不是正常級距上限。播出鏡面仍被 `_broadcast_point_count()` 釘成字極少／字少 3 張、字多／字超多 4 張（`editor_formats.py:154-176`）；D17 雖已裁要取消硬編碼，但尚未實作。

### 為什麼實拍擠在一起

證據非常一致：

- D16 同一篇 276 字、記者版、非卡片：字極少 3點／約41字，字少 3點／約39字，甚至倒掛；字多 6點／131字，字超多 8點／123字（`docs/D16-六檔級距實拍量測-20260915.md:11-27`）。
- 因此底端不是素材太短：同一素材已能撐出 6、8 點。
- 條文本身確實太近：字少明文允許「1～3、不要硬湊3」，它天然會往 1 點靠；字極少只比它多一段 ONE point。
- 模型也沒遵守字極少：實拍出了 3 點，因為程式完全沒替 minimal 設守門。
- 編輯版更受三行範例錨定：`main.py:1478-1479`；這正是 B34 的既有證據。
- 播出鏡面的 3／3 則是版型硬編碼造成，改 density 字串也拉不開，必須等 D17。
- D16 標題上限不是本題主因：該輪兩檔標題只有 6／4 字，遠低於 10／13，上限根本未觸發（量測文件 `:30-40`）。

所以根因排序是：**字少條文允許過低＋minimal/simplified 無硬守門 > 模型未遵守 minimal > 編輯範例與播出鏡面版型壓制**。不是單純把標題 10／13 再調開就會改善。

### 修法候選

1. **只提高字少，建議**  
   將 simplified 改成「素材足夠時 target 4、最低3」，每點約 14～18 個可見字，內文目標約 45～75 字；薄稿仍允許少於3，不湊字。minimal 維持「目標1、驗收容許1～3、硬上限3」。  
   這最直接回應「預設太少」，也不會推翻字極少「一眼看完」的產品定位。

2. **只把字極少往下壓**  
   加程式上限3、目標1、每點≤12；能修「模型不守」，但字少仍可能只出1點，預設太少的原抱怨沒有解掉，不建議單做。

3. **兩者都動**  
   minimal 補上限3；simplified 提高到 target4／最低3。技術上最完整，建議與 B34 同批，但驗收必須把「1～3 都算 minimal 合格」和「simplified 應顯著高於它」分開寫，不能要求每次逐格嚴格不重疊。

### CP1 與重凍成本

- 改 `SIMPLIFIED_DENSITY_RULES` 會改 4 份 simplified fixture：記者／編輯 × safe area／full bleed。
- 改 `MINIMAL_DENSITY_RULES` 本身目前不在 frozen fixture 組內。
- 若為了消除編輯三行範例錨點而改 `EDITOR_SYSTEM_PROMPT_TEMPLATE`，會影響 4 份 editor fixture（standard/simplified × 兩種框）。
- 「ONE point」現行實際位於 `MINIMAL_DENSITY_RULES`，不在 `EDITOR_SYSTEM_PROMPT_TEMPLATE`；MASTER B34 的舊敘述需以現碼更正。
- 重建文字 fixture 不花 API 費。付費成本來自改完後的視覺實拍，不是快照更新。

### 建議目標與驗收

建議目標：

| 檔位 | 點數契約 | 每點 | 內文目標 |
|---|---:|---:|---:|
| 字極少 | target 1；允許1～3；hard max 3 | ≤12 | 約12～30 |
| 字少 | target 4；素材足夠時 min 3 | 約14～18 | 約45～75 |
| 字多 | 現行 min5／target6 | 約24 | 現行不動 |
| 字超多 | 現行 min7／target8 | 約30 | 現行不動 |

驗收建議用 24 張付費圖：2 篇素材（一般敘事稿＋數據稿）× 2 角色 × 2 檔位 × 每格 3 次。以舊文件每張約 US$0.04 估算約 US$0.96，但正式模型／2K 實價需跑前再確認。判準：

- 標題仍守 10／13，不因拉內文而改 D16。
- 播出鏡面先排除，待 D17 落地後另驗；短稿也排除「必須拉開」要求，避免逼模型湊字。

風險為模型隨機性、內容忠實度與資訊量互相拉扯，以及 B34／D17 未同步時編輯版結果仍混濁。改動量中等：1～2個 density block、點數守門、測試與4～6份 fixture。

## 3. B106：「不改字」靜態追查

### 完整路徑

一般 CG、記者／編輯共用同一條資料流：

1. 前端拉桿順序與狀態：`app.js:1221-1231`；切換後存入 `state.digestDensity`，`app.js:1309-1319`。
2. `/api/generate` payload 明送 `density` 與原文：`app.js:2316-2338`。
3. `GenerateRequest` 接收六檔：`main.py:920-921,956-970`。
4. `build_digest_instructions()` 依角色選 reporter/editor 樣板，verbatim 注入兩層覆蓋：`main.py:2345-2415,2459-2477`。
5. token 預算隨原文字數放大、最高24K：`main.py:397-426,3109-3110`。
6. 通用品質檢查後才跑逐字 gate：`main.py:3214-3255`。
7. 後製可能剝外層引號、刪蓋章行、升級底帶標記：`main.py:3280-3289`。
8. 前端把 digest.variable 塞入最終生圖 prompt：`app.js:3178-3208`。
9. 生圖模型實際畫字；回傳圖直接收下，沒有 OCR 比對：`main.py:4024-4041`。
10. refine 以模型改圖，同樣沒有文字差異閘門：`main.py:5385-5483`。

封面不是這條「不改字」模式：

- 封面把 digest controls 隱藏，且 `/api/editor/cover` 不收 density：`app.js:490-516`。
- 十點標題是前端直接送 `title_left/right`，各上限40：`app.js:2563-2584`、`main.py:5916-5919`。
- YT 標題上限60：`main.py:7664-7670`。
- 程式壓字模式會用原標題切行；YT 只接受「去空白後字元完全相同」的 AI 分段，否則 fallback：`editor_formats.py:1172-1205`、`main.py:7890-7899`。
- 十點合成版最多三行，只切不改字，但空白、換行、非日期斜線被當分隔符移除：`editor_formats.py:1218-1239`。
- AI 標題模式仍由影像模型畫字，不能保證像素上無錯字。
- 另一路 `/api/editor/cover-titles` 是「消化標題」而非不改字；會合併空白並硬截40／60字：`main.py:7157-7159,7260-7283`。

### 缺陷候選排序

1. **生圖本身沒有逐字保證——最可能是使用者肉眼所見問題**  
   digest.variable 即使完全正確，最後仍交給影像模型畫中文字；只有 prompt 警告，沒有 OCR 或程式壓字。觸發條件：一般 CG 任一角色，尤其長句、小字、refine 後。

2. **逐字 gate 最後一次明確放行不符結果**  
   `main.py:3241-3255`：前四次擋，第五次只印警告後交付。觸發條件：模型連續五次漏字、換字或加字。這與「不改字」名稱直接矛盾，應列最高優先修復。

3. **專用指令欄只要非空，就完全不做逐字比對**  
   條件是 `not req.user_instruction.strip()`（`main.py:3244`）。即使指令只是「用紅色」「人物放左邊」，gate 也停用。只有明確要求精簡時才應豁免，不能以「欄位有字」代表使用者授權改字。

4. **守門員不驗空白、換行與排版順序**  
   `_VERBATIM_WS_RE = r"\s+"` 並全部移除（`main.py:2767-2768,2828-2834`）。換行、半形空白、全形空白被吞掉後都可能判相同，與 prompt 宣稱「same line breaks」不一致。全半形字元與標點本身會被抓，但空白類不會。

5. **D20 的 `[...]` 指令稿尚未實作，現行會兩頭衝突**  
   gate 只剝 `[標題]`、`[內文小標]`、`<蓋章>`、`<底帶>`；`[大標題]`、`[背景 小插畫]` 仍被當正文。若模型正確地不畫它，gate 判缺字；若照字畫出來，產品語意又錯。證據：`main.py:2767,2828-2841`；MASTER D20 已裁目標，但「如何表示括號是字面文字」尚待裁。

6. **文內指令與 gate 的比對來源不一致**  
   prompt 要求把 `指示:`／`指令:` 行排除（`main.py:2132-2137`），但 gate 直接拿完整 `req.news_text` 比。模型正確排除指令時反而被判不忠實，最後可能落入第2項放行。

7. **蓋章 OFF 會在逐字 gate 通過後刪掉整行**  
   `main.py:3281-3283` 直接移除以 `<蓋章>` 開頭的行；如果那行本來就是使用者完稿的一部分，這是確定性掉字。播出鏡面 OFF 還可能把最後一點改標成 `<底帶>`（`3284-3289`）。觸發條件：不改字＋蓋章 OFF／播出鏡面。

8. **長稿可硬失敗，但不是靜默改字**  
   `VERBATIM_DIGEST_MAX_TOKENS=24000`；20,000字輸入按公式需要42,500，必然撞天花板。finish reason 明確為 length 時會回400或重試失敗（`main.py:3193-3201`），症狀會是「不改字無法生成」，不是少幾個字。

9. **refine 可改未指定文字，B23 同型**  
   refine 只有提示詞約束，沒有把修改前後文字 OCR 比對；`MASTER B23` 已有「佩里姆島→丕林島」實例。觸發條件：任何追加修改，包括只改顏色、位置、人物。

10. **封面上的「不改字」實際上不是拉桿能力**  
    封面隱藏 density。程式壓字路徑相對安全；AI 標題模式、cover-titles 消化入口及 `_clip_title()` 仍會改空白、截字。若使用者以為先選「不改字」再切封面仍有效，現行 UI/資料模型不支持這個期待。

創意拉桿沒有直接改 variable 的程式後製；真正風險仍是模型收到更複雜版面後漏畫小字。來源標籤由 Pillow 後貼，不會吃掉 variable；但 `SYSTEM_DISCLAIMER` 會在前端組 prompt 前以字串 replace 移除（`app.js:3181`），若使用者正文剛好含完全相同句子也會被刪，機率較低。

### 建議做法

先不要等症狀才修所有問題，但也不要把它們混成一刀：

1. 第一刀修確定性缺陷：最後一次不符不得放行；專用指令只有明確要求改寫時才豁免；蓋章後製不得刪 verbatim 正文。
2. 第二刀依 D20 補「指令括號」解析，先裁字面 `[]` 的表達方式。
3. 第三刀再決定產品承諾：  
   - 若「不改字」只保證消化文字，UI 必須明講「影像模型仍可能畫錯字」；  
   - 若承諾成品逐字不變，一般 CG 必須導入程式壓字或 OCR/重生閘門，光改 prompt 不足。
4. refine 另接 B23：修改前後 OCR 或保護未指定文字區，不應假設 B106 修 digest 就會連帶解掉。

### 使用者提供實例後的後台查核清單

請索取「帳號＋時間＋是否按過追加修改」，然後核對：

- `request_id`、`source/action`：digest、web-image、web-refine 或 cover。
- `role`、`density`、`type_label`、版型、stamp、safe_frame、creativity。
- `news_text` 原文與專用 `user_instruction`；逐 code point 比對空白、換行、全半形、標點。
- digest 的 `style`／`structure`／`variable`、`digest_model`、`retry_count`。
- 最終 `prompt` 的 `VARIABLE FIELDS` 是否仍等於 digest.variable。
- `image_model`／provider，以及成品人工/OCR轉錄；藉此分辨「消化先改字」或「生圖才畫錯」。
- 是否有 `finish_reason=length`、quality-check failed、最後一次逐字不符放行等 stdout；成功紀錄目前只保留 retry 次數，不完整保留每次失敗原因，這是觀測限制。
- 若經 refine：比對 refine 前原圖、instruction、refine 後圖，確認未點名文字是否變動。
- 若是封面：確認走 composite 還是 AI title、是否經 `/api/editor/cover-titles`；封面沒有 verbatim density 可查。

## 建議執行順序

1. 先請使用者補 B106 實例，判定是 digest、影像畫字、refine 還是封面認知落差。
2. 先修 B106 的確定性資料損失：最後一次放行、指令欄停用 gate、蓋章後刪字。
3. 同批裁 D20 的 `[]` 字面表示方式，再做指令稿正規化。
4. B105 與 B34 同批：提高 simplified、minimal 補上限；D17 未落地前排除播出鏡面驗收。
5. 最後做 F48；先定座標基準與範圍，再動 enum、prompt、F47/refine 與 UI。

最終待裁清單：

1. F48 採安全區置中或整畫布置中。
2. F48 是否涵蓋播出鏡面、封面；建議兩者皆不納入本案。
3. F48 長來源標籤是否准換行／縮字。
4. B105 是否接受「字極少 target 1、容許1～3；字少 target 4、素材足夠時至少3」。
5. 是否批准更新 CP1 的4～6份 digest fixture；fixture 免費，另批准24張付費實拍。
6. D20 中使用者要如何表達「`[]` 是正文」；建議 UI 勾選框，不靠語意猜測。
7. 「不改字」要承諾消化文字忠實，還是成品像素上的文字也必須逐字正確；後者需要程式壓字或 OCR 閘門。
