# AI 自動消化「標準／簡化」模式設計規格

日期：2026-07-14

## 1. 背景與目標

目前 AI 自動消化會從新聞素材產生 `style`、`structure`、`variable`，但產出的圖表文字有時過多、資訊區塊過雜，導致視覺焦點不明確。

本次新增獨立的「文字密度」設定：

- **標準**：完全保留現有 AI 消化行為。
- **簡化**：AI 依素材動態選擇 1～3 個重點，並採用單一視覺焦點。

文字密度只影響 AI 自動消化，不限制手動模板選擇、手動欄位輸入或最終 Prompt 組合。

本次同時完成原有待辦中的相關一致性工作：

- 上下兩處「記者／編輯」控制同步。
- 全系統圖片規格統一為 1K。
- 更新過時的交接文件。
- 修正目前四個 Ruff 問題。
- 保留已存在但尚未提交的 Final Prompt Output 全寬版面。

「人物／小檔案」第五類不在本次範圍內。

## 2. 設計原則

### 2.1 角色與密度為兩個獨立維度

角色：

- 記者
- 編輯

文字密度：

- 標準
- 簡化

後端以「角色基礎規則＋文字密度規則＋圖表類型」組合系統指令，而不是維護四份內容重複的完整 Prompt。

這種設計允許日後新增「極簡」「詳細」等密度等級，而不必為每個角色複製整份 Prompt。

### 2.2 標準模式向後相容

標準模式必須維持目前的記者與編輯輸出規則，不因新增簡化模式而改變既有工作流程。

### 2.3 簡化模式從生成源頭控制密度

不採用輸出後截斷文字。AI 必須在分析新聞素材時就決定哪些資訊值得保留，並同步設計聚焦構圖，避免刪字後留下語意不完整或構圖仍然擁擠的結果。

## 3. 使用者介面

### 3.1 自動消化區

在新聞文字輸入框與自動消化按鈕之間加入兩組並排的 segmented controls：

```text
文字密度　[標準] [簡化]　　工作角色　[記者] [編輯]

              開始 AI 自動消化整理
```

桌面版兩組設定並排；窄螢幕時允許上下排列。自動消化按鈕維持全寬與主要視覺層級。

預設狀態：

- 文字密度：標準
- 工作角色：記者

按鈕文字必須顯示目前組合：

- `開始 AI 自動消化整理（記者・標準）`
- `開始 AI 自動消化整理（記者・簡化）`
- `開始 AI 自動消化整理（編輯・標準）`
- `開始 AI 自動消化整理（編輯・簡化）`

### 3.2 角色控制同步

原本模板庫上方的「記者／編輯」控制保留。上下兩組控制使用同一個 `state.currentRole`：

- 在自動消化區切換角色，模板庫控制同步更新。
- 在模板庫切換角色，自動消化區控制同步更新。
- 按鈕提示、模板顯示規則與最終 Prompt 角色規則同步更新。

不得建立兩份互相獨立的角色狀態。

### 3.3 文字密度作用範圍

`state.digestDensity` 只用於 AI 自動消化請求。

下列流程不受文字密度限制：

- 手動選擇風格、構圖或視覺模板。
- 手動修改 style／structure／visual／variable。
- 將手動內容組合成最終 Prompt。

## 4. 前後端資料契約

前端呼叫 `/api/generate` 時增加 `density`：

```json
{
  "news_text": "新聞素材",
  "type_label": "資料圖表",
  "role": "記者",
  "density": "simplified"
}
```

允許值：

- `standard`
- `simplified`

後端預設值為 `standard`，確保舊版前端或缺少欄位的請求仍維持現有行為。

## 5. Prompt 組合架構

後端將目前的角色 Prompt 拆成可組合規則：

1. 記者或編輯的基礎規則。
2. 標準或簡化的密度規則。
3. 當前圖表類型。

建議提供可獨立測試的純函式，例如：

```python
build_digest_instructions(role, density, type_label) -> str
```

標準模式不得包含簡化模式的限制文字。簡化模式必須包含下列資訊密度與構圖規則。

## 6. 簡化模式規則

### 6.1 資訊量

- 依素材動態選擇 1～3 個重點，不強迫湊滿三點。
- 不設定固定總字數，以免截斷必要的人名、地名或專有名詞。
- 每個重點只表達一件事，優先使用可在單行讀完的短句。
- 標題、重點與結論不得重複同一事實。
- 移除次要背景、旁支資訊、重複數據及無助於理解主題的細節。
- 多組數據只保留最能說明新聞核心的數據。
- 不得為了填滿版面增加原始素材未提供的文字。

### 6.2 視覺聚焦方式

AI 依素材選擇最適合的一種，不固定為單一構圖。

#### A. 單一主視覺＋最多三個短重點

適合一般新聞、地圖、流程與多數資料題材。

- 只選一個主要地圖、圖表、人物、場景或流程作為畫面主角。
- 其他資訊降為最多三個短標註。

#### B. 大數字或大結論主導

適合素材有一個明顯核心數據或結論時。

- 一個數字或一句結論成為畫面主角。
- 其他資訊降為一至兩個短標籤。

#### C. 主題大圖＋少量文字

適合事故、災害、人物、地點或氣氛導向素材。

- 以場景、照片感示意圖或地圖為主。
- 文字集中在單一區域，保留標題與最多三個重點。

### 6.3 所有簡化構圖的禁止事項

- 不得同時出現多組次要卡片。
- 不得為每個重點加入不必要的裝飾 icon。
- 不得重複呈現相同數據。
- 不得額外補充原始素材未要求的背景資訊。
- 不得為填滿畫面增加文字或視覺模組。
- 不得建立多個彼此競爭的主要視覺焦點。

### 6.4 編輯＋簡化

編輯角色原有文字風格仍適用，包括兩行標題與台灣電視新聞鏡面語法，但密度規則覆寫標準模式的資訊量要求：

- 不強迫輸出 150～180 字。
- 只產生 1～3 個重點。
- `<蓋章>` 改為依內容決定。
- 只有原始素材存在明確結論或可成立的金句時才產生 `<蓋章>`。
- `<蓋章>` 計入最多三個重點，不是額外第四個區塊。

## 7. 1K 規格一致性

本次將畫面、文件與實際請求全部統一：

- Gemini 原生 `image_size` 使用 `1K`。
- GPT Image 2 維持符合模型限制的 16:9 `1280×720` PNG。
- `app.js` 圖片生成請求使用 `1K`。
- `main.py` 的請求模型預設使用 `1K`。
- `index.html`、README、HANDOFF 與模板說明保持一致。
- Notion 模板 Prompt 不得含獨立的 2K／4K 輸出要求；圖片檔名中的字串不算解析度規格。

## 9. 測試與驗證

### 9.1 後端規則測試

使用標準函式庫 `unittest`，不新增測試依賴。至少驗證：

- 缺少 density 時預設為 `standard`。
- 記者＋標準不含簡化規則。
- 編輯＋標準維持目前規則。
- 記者＋簡化包含動態 1～3 點及三種聚焦方式。
- 編輯＋簡化包含可選 `<蓋章>`，且蓋章計入三點上限。
- 不合法的 density 被請求模型拒絕。

### 9.2 前端互動驗證

使用瀏覽器攔截 `/api/generate`，不呼叫付費 API：

- 預設顯示「標準＋記者」。
- 文字密度可以切換。
- 上下兩組角色控制雙向同步。
- 自動消化按鈕文字隨狀態更新。
- 請求 body 正確帶入 `role` 與 `density`。
- 手動欄位與最終 Prompt 不因切換密度而被修改或截斷。
- 桌面及窄螢幕版面均可正常操作。

### 9.3 靜態與資料驗證

- `node --check app.js`
- Python compile
- `uv run ruff check`
- `uv lock --check`
- `python -m unittest`
- `git diff --check`
- `templates.json` 可解析且維持 205 筆
- 模板 Prompt 沒有獨立的 2K／4K 規格

### 9.4 完成前限制

除非使用者另行要求，不呼叫需要計費的 AI 消化或圖片生成 API。功能驗證以本地規則測試、瀏覽器請求攔截及實際 UI 操作完成。
