# 創意拉桿模組化計畫（2026-09-11）

使用者：「所有 YT 版型如果都加創意拉桿（照搬十點不一樣那套），是否把創意拉桿這個
功能改模組化，比較方便管理？」「還要考量記者與編輯一般版型現在也有創意拉桿，
整個網站的創意拉桿功能都是模組化範疇。」

## 判準：現在到底該不該抽

`compose.py` 開頭已經寫下這個 repo 的判準：

> 本模組刻意**不做**通用的圖層 DSL——目前只有兩個版型，兩個版型不值得一個直譯器。
> 出現第三個版型時再抽表。

套到創意拉桿：**已經三處，而且第三處（YT）才剛長出來。** 過門檻了。

## 真正要解決的問題（不是「程式碼重複」）

1. **「拉桿不准碰的東西」有三份定義，其中一份不存在。**
   CG 的 (a)(d)(e)(f) 與十點的 (a)(b)(e) 講的是同一批事（不准改字、不准新增文字、
   每字完整可讀、繁中臺灣形），各寫各的英文。YT 那條**一句都沒有**——
   2026-09-11 實拍 L1 配色跑掉（指定紅底白字、畫成白底黑字）、四張位置全擠在
   上半部偏左，就是沒有框住的結果。新版型只要照現在的方式長出來，就會再缺一次。

2. **等級名稱前後端各一份。** `CG_CREATIVITY_LEVEL_NAMES`（Python）與
   `CG_CREATIVITY`（app.js）是兩份手寫清單，`COVER_AI_TITLE_LEVEL_NAMES` 同理。
   這個 repo 已經為同類問題建過護欄（`tests/test_prompt_parity.py`：
   `news_prompt.py` vs `app.js` 兩份規則同步），照抄那個做法即可。

3. **三條鐵律只寫在十點那套的註解裡。** 「數字釘在 CANVAS 正後方」「矛盾要拆掉
   不能靠後面覆蓋」「可數、要分支的一律交給程式」——2026-09-11 一天之內因為
   忘記第二條踩了三次（L2/L3/L4 的許可句、`COLOUR EACH LINE` 孤兒規則、
   YT 的 `no dates`）。它們該是模組的結構，不是註解裡的叮嚀。

## 目標與非目標

**要抽的是機制：**
- 等級常數、中文名稱、前後端同步護欄
- 變化池與「一顆 seed ＝ 一種長相」的抽籤
- 「等級 → 一組設計參數」的表格形狀
- 共用的 FIXED 段（不准改字、不准新增文字、可讀性、繁中、不准為了排版生素材）
- 「RNG 只換風格不換響度」那條界線

**不抽的是數字：**
- 標題塊高度 18/24/30/36%、字級比 1.8/2.5/3、配件數 0/0/1/2/3
- 保留區座標、行清單格式、seam 幾何、各版型的貼圖區

理由是 2026-09-11 學到的那條：**訂數字之前先量現行成品**。十點那組數字是量十點的
播出成品訂的（標題塊實際佔畫面高度約 18–25%）。YT 整點的標題底在 96.5%、
十點在 91.5%，兩者尺度不同，直接搬會重演「我憑感覺訂，一訂就是兩倍」。
每個版型自己帶一張數字表，模組只吃表。

## 模組介面

新增 `creativity.py`（不要再往 `editor_formats.py` 堆，它已經超過 1500 行）。

```python
LEVEL_MIN, LEVEL_MAX = 0, 4
LEVEL_NAMES = {0: "規矩", 1: "微設計", 2: "有設計", 3: "奔放", 4: "最狂"}

# 變化池（從 editor_formats 搬過來，內容一字不改）
PLATE_SHAPES: tuple[str, ...]
STAGGER_PATTERNS: tuple[str, ...]
TYPEFACES: tuple[str, ...]
PALETTES: tuple[tuple[str, str, str, str], ...]
ANCHORS: tuple[str, ...]
TILT_DIRECTIONS: tuple[str, ...]
ACCESSORY_SHAPES: tuple[str, ...]

@dataclass(frozen=True)
class Draw:
    """這一次抽到的風格。只換風格，不換響度。"""
    plate: str
    stagger: str
    typeface: str
    palette: tuple[str, str, str, str]
    anchor: str
    tilt: str

def draw(level: int, seed) -> Draw:
    """同一顆 seed 一定抽到同一組。抽籤順序固定，動了就換掉所有既有 seed 的長相。"""

def fixed_block(*, target: str) -> str:
    """拉桿不准碰的東西。target='digest'（CG 那條，管 structure 的委製內容）
    或 target='image'（十點／YT，管生圖）。共用的條目只寫一次。"""
```

各版型保留自己的組句函式，只是改成吃 `Draw` 與自己的數字表：
`editor_formats.cover_design_brief(level, spec=COVER_TITLE_BRIEF_SPECS, draw=...)`、
`yt_hourly_date_clause(level, draw=...)`、`main.cg_creativity_rules(level)`。

## 分階段

每一階段自己跑得完、自己驗得完，中間任何一階段停手都不會留下半成品。

### P1 — 抽出 FIXED 段（最高價值，風險最低）

把 CG 的 (a)(d)(e)(f)、十點的 (a)(b)(e) 之中**語意相同**的條目合成一份
`creativity.fixed_block()`，版型專屬的條目（CG 的點數／安全留白／禁地圖，
十點的標頭帶／seam／面板歸屬）留在原地。

- 護欄：`tests/test_reporter_prompt_frozen.py` 是紅線——CG 那條注入的是消化
  prompt，動到記者版 prompt 就紅。**紅了就是改壞了，去改程式不要改 fixture。**
- 驗收：合成後的 prompt 與合成前逐字元 diff，語意相同的條目允許措辭統一，
  其餘必須一字不差。
- 附帶成果：YT 立刻補上它現在缺的那一段（實拍 L1 配色跑掉就是它擋得住的）。

### P2 — 等級名稱單一真相源 ＋ 前後端 parity 測試

`creativity.LEVEL_NAMES` 一份，`app.js` 從同一份生成或由測試比對。
照 `tests/test_prompt_parity.py` 的做法。

### P3 — 抽出變化池與 `draw()`

把七個池子從 `editor_formats` 搬進 `creativity`，內容一字不改，
`cover_design_brief` 改成呼叫 `creativity.draw()`。

- 護欄：`test_the_rng_changes_style_never_loudness` 必須維持綠燈。
- **抽籤順序不可以動**：順序變了，所有既有 seed 的長相就全變了。
  搬家時逐項對照，並加一個測試釘住「同一顆 seed 在搬家前後抽到同一組」
  （搬家前先把幾組已知輸出記進 fixture）。

### P4 — YT 三種版型各自接上拉桿

每個版型做三件事，缺一不可：
1. 請求加 `creativity` 欄位（YT 整點已有）。
2. **量自己的成品**，訂自己的數字表——不要抄十點的 18/24/30/36%。
3. 組自己的條文，吃 `creativity.draw()` 與 `fixed_block(target="image")`。

順序建議：整點（已有基礎）→ 國內外新聞直播 → 今日熱搜。
每個版型實拍 L1–L4 各一張驗收，重點看**保留區有沒有被侵入**——
2026-09-11 `73ae198` 的教訓：排除條文埋在一長串否定句中間模型會照犯，
要把排除句拆成每件招式後面各掛一句 `←`。

### P5 — 前端共用拉桿元件

`index.html` 現在兩條拉桿各自一段 HTML。抽成一個元件，等級名稱來自 P2 的
單一真相源。這一步純 UI，最後做。

## 風險

1. **`test_reporter_prompt_frozen.py` 誤傷。** CG 那條走消化 prompt，記者版
   prompt 是凍結的。P1 動到共用條文時最容易踩。每一步都跑全套。
2. **抽籤順序被動到。** P3 最大的風險，會靜默改變所有既有 seed 的長相，
   測試不釘就看不出來。
3. **把數字一起抽走。** 最容易犯的錯，也是這份計畫反覆強調的那條。
   模組裡**不准出現任何版面尺寸的百分比**，可以加一個測試掃 `creativity.py`
   的原始碼，出現 `%` 或像素數字就紅。
4. **CG 與封面的注入目標不同。** 一個進消化 prompt、一個進生圖 prompt，
   `fixed_block(target=...)` 不能混用——寫給生圖模型的「不准畫地圖」跟寫給
   文字模型的「不准在 structure 裡委製地圖」不是同一句話。

## 不做什麼

- 不做通用的「條文 DSL」。抽的是資料（池子、等級表）與一段共用條文，
  不是一個把 prompt 組出來的直譯器——那是 `compose.py` 註解裡明講要避免的東西。
- 不統一各版型的條文措辭。每個版型的 prompt 都是實拍調出來的，
  措辭統一等於把調校成果洗掉。
- 不在這份計畫裡處理「側標／小籤創意 3/4 自動生成」（使用者已裁決要做，
  但那是內容問題不是拉桿問題，另案）。

### 計畫書當時沒料到的三件事

1. **P1 的「語意相同的條目允許措辭統一」跟凍結測試打架。** CG 那段的項次
   字母 (a)–(i) 本身就是 `test_reporter_prompt_frozen.py` 釘住的位元組，
   抽走幾條再重編號必紅。最後的形狀是「跨 target 共用結構、target 內共用
   文字」：`target="digest"` 逐字元搬家，`target="image"` 才真的統一。
2. **十點抽 6 顆、YT 只抽 5 顆**（YT 沒有 anchor 那一顆）。計畫書以為 YT
   沒有 RNG。若讓 `draw()` 寫死抽 6 顆再叫 YT 忽略 anchor，YT 的 tilt 會從
   第 5 抽變成第 6 抽，所有既有 seed 的傾斜方向全變而測試看不出來。
   所以 `anchor=False` 是**連抽都不抽**。
3. **P4 幾乎不用做，P5 才是唯一使用者看得到的成果。** 計畫書寫 P4 是大宗
   （每版型半天、大量實拍），但 YT 後端 2026-09-11 當天稍早就做完了；
   反而是「YT 前端根本沒有拉桿、線上按不到」這件事計畫書完全沒寫。

### 這次新學到、值得記住的

- **拿掉編號時要記得編號兼任分隔符。** P1 拆掉 (a)(b)(c)(d) 之後四條硬規則
  糊成一段無分隔長段落，最後一條最容易被模型吃掉。改用換行補回分界。
- **fixture 必須在動程式之前產生，而且要獨立驗證它真的是之前產生的。**
  這次兩支 RNG fixture 都用「把改動 stash 掉、用舊 HEAD 重放」驗過。
  搬完才產的 fixture 只能證明程式跟自己一致。
- **變異測試是驗護欄的唯一方法。** P2 改 `app.js` 一個字、P3 對調兩抽，
  兩支護欄都確實轉紅。
