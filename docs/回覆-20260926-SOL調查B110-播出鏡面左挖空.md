## 結論

問題不是「左側挖空」的幾何計算壞掉，而是有兩條會產生相同症狀的路徑：

1. 前端預設 `hole=OFF`，但仍允許／顯示左側方向；使用者只選左側時，實際送出的 `broadcast_hole` 是空字串。上傳圖又預設為 `asis`，模型便依指令把原圖放入版面。
2. 另有一個已確認的 D24 回歸：即使真的開啟挖空，只要是「編輯＋安全框 OFF＋字多／字超多」，後端會在 finalizer 直接返回原圖，連明確要求的左、右挖空都跳過。

`asis` 本身不會清除挖空；問題是挖空沒有被啟用，或在後端被 `safe_frame=False` 的分支略過。左、右在相同條件下行為一致，未發現左側專屬的 compose bug。

## 最小重現條件

### 路徑 A：目前 UI 最容易發生

1. 角色選「編輯」。
2. 版型選 `broadcast`。
3. 方向選左側，或接受切版後預設的左側。
4. 不另外開啟「壓框」；維持預設 OFF。
5. 上傳一張圖片，保留預設用途 `asis`。
6. 送出。

結果：`broadcast_hole=""`，沒有白色挖空；模型收到 asis 指令，將原圖直接置入版面。

沒有上傳圖時仍不會挖空，只是不會出現「原圖置入」；改成 `aiedit` 時仍不挖空，但圖片會偏向重繪。

### 路徑 B：後端 D24 回歸

1. 角色選「編輯」。
2. 版型選 `broadcast`。
3. 明確開啟壓框，方向左或右皆可。
4. 關閉安全框。
5. 密度選「字多」或「字超多」。
6. 上傳圖可有可無；若為 `asis`，外觀最接近本次回報。

結果：後端明知 `broadcast_hole=left/right`，仍在 finalizer 提前返回，沒有挖空。

若回報堅稱「右側正常、左側異常」，建議比對兩次請求中的 `broadcast_hole`、`safe_frame`、`density`。在相同 payload 下，本地 compose 與 fake 生圖左右均通過，沒有重現 side-specific 差異。

## 修法建議

### 必修：後端保證明確的 hole 不被 frame plan 吃掉

最小修改位於 [main.py:4334](E:/GitHub/TVBS-AICG-PG/main.py:4334)：

- `safe_frame=False` 時，不再無條件直接返回。
- 若 `broadcast_hole` 有值，對原始生圖結果單獨執行 `apply_broadcast_hole_response()`。
- 保留挖空前圖片為 `source_image_base64`，避免後續 refine 疊加或失去原始來源。

不建議直接強迫 `needs_frame=True`，那會破壞 D24「安全框 OFF＋字多不加框」的既有目的。應只補使用者明確指定的白色 hole。

預計修改：

- `main.py`
- B110 新測試，或擴充 `tests/test_broadcast_hole_switch.py`

### UI 語意修正

建議二選一：

- 點擊「左側／右側挖空」時自動令 `state.hole=true` 並刷新壓框按鈕；或
- 保留預設 OFF，但 hole OFF 時禁用／淡化方向按鈕，文案改成「影片區方向」，清楚提示必須先開啟壓框。

第一種較符合使用者直覺，但會改變 2026-09-07 確立的預設 OFF 行為，需要產品裁決。

### 測試需求

至少增加：

- `safe_frame=false + density=standard/maximum + broadcast_hole=left/right`，確認指定區域為白色。
- 左右 × `asis/aiedit/無圖`，確認圖片用途不會改寫 `broadcast_hole`。
- 確認挖空後仍保存未挖空的 source image，供 refine 重做。
- 前端測試明確驗證選方向後 hole 的產品決策，不再只驗證按鈕或字串存在。

現有相關 127 個單元測試皆通過，但沒有覆蓋「hole × safe frame OFF × 字多」這個交叉組合。

### 是否需要付費實拍

核心修正不需要付費實拍，Pillow 挖空可用本地假圖完整驗證，必要張數為 **0 張**。

若要驗收 `asis` 與挖空並存時的視覺排版，建議選配 **2 張**付費實拍：同一素材各跑左、右一次。
