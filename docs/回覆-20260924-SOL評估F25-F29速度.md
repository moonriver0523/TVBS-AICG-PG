### Cloud Run 與 BackgroundTasks／thread

FastAPI `BackgroundTasks` 的確會在回應送出後執行工作，但它仍是同一個 container 內的工作，不是耐久佇列。[FastAPI 官方說明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

Cloud Run 預設的 request-based billing 只在處理 request 時配置 CPU；instance-based billing 才適合回應後的短期背景工作，而且會改成整個 instance 生命週期計費。[Cloud Run billing settings](https://docs.cloud.google.com/run/docs/configuring/billing-settings)

即使開 instance-based billing：

- idle instance 仍可能被回收；
- SIGTERM 後只有 10 秒 grace period；
- 尚未完成的上傳／本機寫檔仍可能遺失。[Cloud Run container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)

背景 thread 還多一個本專案特有風險：新 thread 不會自動繼承登入者 context；現有串流實作已特別記錄並手動複製 context，見 [main.py:3407](</E:/GitHub/TVBS-AICG-PG/main.py:3407>)。F29 若直接在 `_archive_generation` 開 thread，可能再次漏掉 `user_id/email/name`；必須在回應前把使用者與完整 payload 固化成不可變資料。

### 後台是否依賴回傳前已歸檔

沒有程式上的自動依賴：前端生成完成後不會自動呼叫 `/admin`。但有明確的一致性依賴：

- `/admin` 每次即時掃 audit JSON，[admin_console.py:366](</E:/GitHub/TVBS-AICG-PG/admin_console.py:366>)。
- audit JSON 是整筆紀錄最後才寫；背景尚未完成時，後台看不到這筆。
- 若 instance 在背景工作完成前回收，後台會永久漏列；`request_log` 無法補位，因為 `/admin` 不讀它。
- `audit_archive` 的設計目的明列為長期稽核且不自動清除，見 [audit_archive.py:1](</E:/GitHub/TVBS-AICG-PG/audit_archive.py:1>)、[audit_archive.py:10](</E:/GitHub/TVBS-AICG-PG/audit_archive.py:10>)。純 in-process best-effort 背景化與這個要求衝突。
