# 新聞 CG Prompt 生成器 — App 化 × Notion 直連 規劃書

> 目標：讓工具的模板庫「即時」來自你的 Notion 資料庫。你在 Notion 新增一筆圖表 prompt，工具下次載入就自動多一個模板，全程不需要人工搬移。

---

## 一、核心觀念：從「內建資料」改成「即時資料源」

目前 V8 的模板是寫死在 `CHART_TYPES` 這個 JavaScript 物件裡（內建資料）。App 化的關鍵一步，是把這個物件的來源，從「寫死在檔案裡」換成「開啟時去 Notion 撈」。

```
現在：  HTML 檔  ←（寫死）←  CHART_TYPES 物件
未來：  App 前端  ←（API 撈）←  後端  ←（Notion API）←  你的 Notion 資料庫
```

一旦這條線接通，你的 Notion 就是唯一的「真實來源」（single source of truth）。工具只是它的一個漂亮讀取介面。

---

## 二、為什麼需要「後端」，不能前端直接連 Notion

這是整個規劃最重要、也最容易踩雷的一點。

Notion API 需要一把「金鑰」（Integration Token）才能讀取資料。**這把金鑰絕對不能放在前端**（也就是使用者瀏覽器看得到的 HTML／JS 裡），因為任何人打開開發者工具就能偷走，等於把你整個 Notion 工作區的鑰匙公開。

所以中間一定要有一個**後端**當守門員：

```
使用者瀏覽器  →  你的後端（藏著 Notion 金鑰）  →  Notion API
   （安全）          （金鑰只存在這裡）           （回傳資料）
```

後端做三件事：保管金鑰、代替前端去問 Notion、把 Notion 的原始資料整理成工具好用的格式再回傳。

> 這也解釋了為什麼現在這個 HTML 檔單獨下載到你電腦上開，「AI 消化」會失效——因為它也是同樣的架構問題，API 呼叫需要一個受保護的環境。App 化會一次解決這兩件事。

---

## 三、資料對映：Notion 欄位 → 工具三層變量

你的資料庫已經幫我們把分類做好了，這是最大的優勢。對映關係如下：

| 工具需要的 | 對應你的 Notion 欄位 | 說明 |
|---|---|---|
| **圖表類型**（頂層四大類） | `構圖TAG` / `用途 TAG` | 用來判斷這筆該歸到資料圖表／情境／地圖／3D 哪一類 |
| **風格**（style） | `✠ 風格包` | TVBS藍經典、CNN紅、Bloomberg… 直接對應 |
| **構圖 + 資料範本**（structure + template） | 頁面內文「範例完整 prompt」摺疊區 | prompt 全文，需要拆成「佈局規則」與「可替換變量」 |
| **模板名稱** | `名稱`（title） | 顯示在工具標籤上的名字 |
| **是否精選** | `⭐` | 可用來決定哪些模板優先顯示 |

### 關鍵利多：prompt 位置固定

你已確認「每筆 prompt 都固定藏在『範例完整 prompt』摺疊區的程式碼區塊裡」。這一致性極為重要——它讓後端可以用一條穩定規則抓取全文，不需要每筆猜位置。抓取邏輯就是：

> 進入頁面 → 找到 `<details>` 摘要為「範例完整 prompt」的區塊 → 取出裡面 ```` ```code ``` ```` 的內容 → 那就是 prompt 全文。

建議把這個規則當成資料庫的「隱形合約」：只要你之後新增的每一筆都維持這個擺放習慣，後端就永遠抓得到。

## 四、四大類型的自動判斷規則（建議）

後端撈到每筆的 `構圖TAG` / `用途 TAG` 後，用以下規則歸類（可依實際情況調整）：

- **資料圖表**：構圖TAG 含 `儀表板`、`長條圖`、`折線圖`、`圓餅圖`、`對照圖`、`列點格`，或用途TAG 含 `股匯市`、`價格`、`民調`、`企業財報`、`體育成績`
- **地圖／位置**：構圖TAG 含 `♖ 地圖`、`航跡圖`，或用途TAG 含 `世界地圖`、`位置距離`、`地震`、`天氣`
- **3D示意／流程**：構圖TAG 含 `流程軸`、`時間軸`、`拆解圖`、`透視圖解`、`生態剖面`、`3D模型`、`3D微縮`，或用途TAG 含 `拆解流程`
- **情境示意圖**：構圖TAG 含 `情境圖`、`♖情境小劇場`、`肖像`、`照片`，或用途TAG 含 `情境劇場`
- **落單的**：都不符時，歸到「資料圖表」或另設「其他」，避免遺漏

> 一筆可能同時符合多類（例如「時間軸地圖」）。建議允許一筆出現在多個類型底下，而不是強制單選。

## 五、實作路徑：三個階段，由簡入繁

### 階段 A：半自動「批次匯出」（最快、最省，不需要工程）
不做即時連線，改成「定期快照」。做法：
1. 由我（在對話中）用 Notion 工具，一次讀取一批頁面
2. 我把它們拆解、對映後，直接產生更新版的 `CHART_TYPES` 資料檔
3. 你拿到新的 HTML／資料檔，模板就更新了

**優點**：零工程、零金鑰風險、馬上能用。
**缺點**：不是即時，每次要新模板得回來找我重生成。適合你「還在累積、還沒到上百筆天天變動」的現階段。

### 階段 B：後端 + 前端分離（真正的 App，需要一點工程）
1. 建一個輕量後端（Cloudflare Workers、Vercel Serverless、或 Node/Python 小服務都行）
2. 後端存 Notion 金鑰，提供一個 `/templates` 接口
3. 接口內部：查詢資料庫 → 逐頁抓摺疊區 prompt → 套用第四節的分類規則 → 回傳整理好的 JSON
4. 前端（就是現在的介面）開啟時打這個接口，用回傳的 JSON 動態建出 `CHART_TYPES`
5. 加一層「快取」：Notion 資料不會每秒變，後端可以每 10 分鐘或每小時更新一次，避免每個使用者都戳 Notion（也避免撞到 API 速率限制）

**優點**：真正即時，你改 Notion、工具就跟著變。
**缺點**：需要部署與維護一個後端。

### 階段 C：加值功能（有了後端之後的延伸）
- **反向寫入**：在工具裡調好一組新 prompt，一鍵存回 Notion 成為新的一筆
- **縮圖**：把你 Notion 裡存的成品圖也一起撈出來，讓使用者選模板時看得到長相
- **搜尋／篩選**：用你既有的 `風格TAG`、`標籤`、`⭐` 做多維度篩選

---

## 六、務必注意的坑

1. **金鑰保護**：重申一次，Notion 金鑰只能在後端。前端出現金鑰＝資安事故。
2. **API 速率限制**：Notion API 大約每秒 3 次請求。上百筆頁面若逐一抓內文，要分批＋快取，不能一次全打。
3. **圖片 URL 會過期**：你頁面裡那些 S3 圖片連結帶有時效簽章（看網址裡的 `X-Amz-Expires`），過幾分鐘就失效。若階段 C 要顯示縮圖，得讓後端每次即時重新取得，不能存死連結。
4. **摺疊區合約**：整套自動化建立在「prompt 固定放在『範例完整 prompt』摺疊區」這個習慣上。哪天你改了擺放方式，抓取就會漏。建議把這條寫進你資料庫的使用守則。
5. **prompt 內的變量標記**：你的 prompt 用 `[ ]` 標指令、`< >` 標可替換內容、`@id` 引用圖片。後端拆解時要保留這套語法，工具才能正確把「哪些是使用者要改的變量」標出來。

---

## 七、我的建議

以你「還在持續累積模板、目前一小部分進了工具」的現況，**先走階段 A**：接下來你想擴充模板時，告訴我要哪一批（某個類型、某個風格包、或某幾筆星號精選），我直接從 Notion 讀、拆解、生成更新版工具給你。這條路現在就能動，不必等任何工程資源。

等到你覺得「回來找我重生成」變得頻繁、或模板量大到想要即時同步時，再啟動階段 B。那時這份文件的第二到第六節，就是給工程師（或你自己）的完整施工圖。
