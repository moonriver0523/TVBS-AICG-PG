## Stage 1 — 穩定 digest 額度與有效重試（D21、B50）

建議 commit：`fix: stabilize digest token budget and retries`

### 修改

- `main.py`
  - `DIGEST_MAX_TOKENS`：只把 6000 改成 12000。不要改 `DIGEST_DEADLINE_SECONDS`、attempt 數、timeout、`digest_reasoning_body()` 的一般預設與 prompt 本文；也不要新增 `reasoning.effort` 或 `provider.require_parameters`。
  - `digest_completion()`：新增 optional 的 `retry_context` 與 `reasoning_max_tokens` 覆寫入口。`retry_context` 只附加在 user message 尾端，不改 system prompt；未傳時產生的 payload 要與現況相同。
  - `generate()` retry loop：保存上一輪的「標準化失敗原因」，下一輪傳入明確修正訊息，例如 JSON 解析失敗、缺欄位、品質檢查原因或 upstream 失敗及 attempt 編號，使每次 retry request bytes 不再相同。若 `finish_reason == "length"`，或錯誤可判定為 reasoning/output budget 截斷，下一輪額外把 reasoning max 降至 1024；其他失敗仍沿用既有 reasoning 設定。
  - request 差異不可用隨機 nonce 假裝完成；必須能從內容看出上一輪為何失敗。log 中只記分類後原因，避免把 provider response 或敏感內容整包寫入。

### 測試與驗收

- `tests/test_generate_retry.py`
  - mock 連續兩次品質失敗再成功，序列化比較三次送往 provider 的 request body，斷言皆不相同且包含前一輪失敗類別。
  - mock `finish_reason=length`，斷言第二次 `reasoning.max_tokens == 1024`；非 length 品質失敗不得誤降。
  - mock transport exception 後成功，斷言第二次仍有 attempt/upstream retry context，因此不是 byte-identical。
  - 驗證 system prompt 在各次重試完全相同，避免 B50 順帶破壞凍結 prompt。
- `tests/test_digest_reasoning.py`（若現有名稱不同，併入最接近的 token-budget 測試檔）：斷言總 output 上限為 12000，而既有一般 reasoning 配額與 timeout 常數未變。
- 本 Stage 不實打模型；成本、時間與實際 finish reason 留到文末人工核准項。

  - `COVER_EXCLUDED_PEOPLE_BLOCK`、`PORTRAIT_NO_REFERENCE_RULES` 等舊的背影／剪影 fallback 改為 no-person scene。第二次仍出現 excluded name 時由 deterministic sanitizer/validator 擋下，不再交給模型自行決定。
  - `apply_portrait_to_image_request()` 即使 subjects 為空也不得繞過 Stage 4 baseline；入口只負責 mode-specific append。
- `news_prompt.py`
  - 新增 entry-only、no-entry、replacement 三種清楚分離的規則。
  - `PORTRAIT_WITH_REFERENCE_RULES`、`PORTRAIT_MULTI_WITH_REFERENCE_RULES`、`USER_REFERENCE_PORTRAIT_RULES` 統一改為「寫實新聞肖像優先，僅帶輕微插畫筆觸」，禁止退回「明顯手繪／卡通」，但也不得宣稱照片級身份驗證；保留示意圖標示與既有多人安全限制。
- `main.py refine_image()`
  - `replacement_person` 非空時執行同一 lookup：有上傳對應 portrait 則優先；否則有 Wikipedia photo 就附為 reference；只有條目無 photo 時允許模型畫並回 notice；無條目則 400，不能假裝完成換臉。
  - prompt 明確鎖定「只替換目標臉，其他人物、構圖、文字、logo 不變」。一般 refine（未填 replacement）行為不變。

### 測試與驗收

## Stage 6 — 封面追加修改與原圖標題層（B51、B52、B55、A8）

建議 commit：`fix: preserve cover composition during refinements`

這四項共用 `handleRefine()`、cover source/base 與 recompose 流程，拆開會反覆改同一段狀態機，因此合併成一個可端到端驗收的 Stage。

### 修改

- `app.js`
  - `applyEditorFormatLocks()`：五個會生圖的封面版型（十點不一樣、YT 國內外新聞直播、YT 整點直播、YT 今日熱搜，以及其共用 cover mode）在隱藏 safe frame/stamp 控制時，同步把 UI state 與送出 payload 強制設為 `safe_frame=false`、`stamp=false`。切回非封面才恢復該角色原本偏好，不讓隱藏值污染請求。

- `compose.py`

## Stage 8 — 編輯高密度高解析度生成與輸出（F38）

建議 commit：`feat: raise resolution for dense editor graphics`

此 Stage 最後做，因解析度會放大成本與延遲，需先有 Stage 2 的計時/provider 稽核，且上線前必須完成價格 checkpoint。

### 修改

- `main.py`
  - `ImageGenerateRequest` 新增 `density: str = ""`；`handleOneClickGenerate()`、`generate_news_image()` 及封面 caller 傳遞現有 density。決策函式只在 `safe_frame_profile == "編輯"` 且 density 為 `standard` 或 `maximum` 時回傳 high-res profile。
  - `NATIVE_GPT_IMAGE_SIZES` 不直接全域改值；新增 request-aware `image_generation_size(req)`：高解析 profile 的 16:9 為 2560×1440（若 provider 原生參數只能選離散尺寸，使用官方支援的最接近且不低於現況者，再於本地輸出 2560×1440）；一般 profile 保留現在 1280×720。21:9 只在真的符合編輯＋標準／極高時用同比例 3360×1440，其他仍為 1680×720。
  - `_openrouter_gpt_size()` 與原生 GPT transport 都接收同一個 resolved size，禁止兩條 provider 各自算一次。
  - `finalize_image_result()`、`frame_image_response()` 接收 resolved output canvas；高解析 profile 傳 2560×1440／3360×1440，其他仍用 `safe_area_spec.BASE_CANVAS`。回應的 `source_image_base64` 保持 provider 原圖，final image 才是 frame/compose 後輸出。
- `safe_frame.py`
  - `apply_safe_frame()`／`safe_rect()` 以顯式 canvas 參數縮放既有 normalized safe-area 比例；不要修改 module-level `DEFAULT_CANVAS` 造成其他 request 連帶升級。
- `app.js`
  - 一般一鍵生圖 request 帶 `state.density`；記者、低密度與所有未指定 density 的舊路徑不變。

### 測試與驗收

- `tests/test_image_model_defaults.py`：role × density × provider × aspect ratio decision table。只有 editor/standard、editor/maximum 命中 high-res；reporter、editor/low、空 density 全保持舊 size。
- `tests/test_safe_frame.py`：1920×1080 舊 golden/座標不變；2560×1440 與 3360×1440 的安全區按比例縮放，ON/OFF profile 的最終像素尺寸符合各自既有 frame semantics。

## 風險與回滾

- **Prompt 凍結擴散**：Stage 3 是唯一允許重凍的點。若 diff 超出 B57/F41 對應段落，整個 Stage 回滾，不接受以批次更新 snapshot 掩蓋非預期變更。
- **重試成本增加**：B50 會讓 retry request 真正改變，但 attempt 數不增加；若 production latency/成本惡化，只回滾 retry-context/reasoning override，不回退 D21 的 12000 上限，兩者由獨立函式與測試隔離。
- **稽核資料相容性**：新欄位皆 optional/default，reader 先相容舊 record 才寫新 record。若後台渲染出錯，可單獨回滾 UI，保留已寫入的 additive metadata。
- **人物誤判**：四層 lookup 必須用 typed outcome，不可再用 `None` 同時代表「無條目」與「無照片」。若 lookup service 不穩，fail closed 到無人物場景，不得 fallback 成具名捏臉。
- **封面像素保真**：title mask 算錯可能切到 logo/臉。以 mask 外 hash 與固定元素座標測試作 release gate；失敗時回滾 title creative 路徑，保留普通本地壓字。
- **解析度成本／記憶體**：高解析圖會增加 base64、Pillow 記憶體與 archive 容量。以 feature flag 控制，發生 timeout/OOM 可關閉 high-res profile，舊解析度決策仍完整存在。
- **前後端版本錯位**：所有新增欄位都有預設；後端先部署、前端後部署。回滾前端時後端仍接受舊 payload，回滾後端前要先停用前端送出的新欄位功能。
