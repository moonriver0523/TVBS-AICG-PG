> ⚠ 擷取時用了 tail -120，**開頭的結論段被截掉**，本檔自選項 1（require_parameters）起。

- `require_parameters=true`：先排除不支援所有參數的 provider。
- `allow_fallbacks=true`：仍可在**符合參數條件的候選集合內**繼續 fallback。
- 如果沒有符合者，請求會直接失敗，而不是靜默拿掉參數。[OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)

所以兩者不衝突，但會形成「先過濾，再 fallback」。

然而 R6 十次都已經是 Anthropic，而且 Sonnet 5 官方明說 `max_tokens` 會被忽略，因此這不是 provider 輪替造成的間歇問題。`require_parameters` 最多改善 [strict JSON schema](/E:/GitHub/TVBS-AICG-PG/main.py:1015) 的路由確定性；OpenRouter 本身也建議 structured output 搭配它，但同時提醒不同 provider 的 strict 程度仍可能不同。[OpenRouter structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs)

**建議：可以加，但列為第二層防護，不要拿它做第一輪付費驗證的主變因。**

### 2. `reasoning.effort`

現行 [digest_reasoning_body()](/E:/GitHub/TVBS-AICG-PG/main.py:243) 對 Sonnet 5 實際等同沒有控制：`max_tokens` 被模型忽略後，Sonnet 5 以預設 `high` adaptive thinking 執行。

建議：

- 第一輪：`reasoning: {"effort": "low"}`。
- 不建議先試 medium：速度是第一順位，應先驗 low 的品質底線。
- 如果 low 仍明顯超時，可把 `enabled:false` 列為額外實驗組；它理論上最快，但漏規則風險比 low 高，不宜直接上線。
- 12,000／16,000 先保留作輸出保險，不再增加。

這項不需要改 prompt，只需要改 payload 組裝與相關測試。

### 3. 截斷降級重試

目前程式其實已在 `length` 後把下一次 reasoning 設成 1,024，但因 Sonnet 5 忽略 token budget，這個降級同樣不會生效；而且仍使用完整 system prompt。[重試迴圈](/E:/GitHub/TVBS-AICG-PG/main.py:2724)

R6 的截斷常在 125～201 秒才發生。到那時才啟動第二次呼叫，已經不可能滿足兩分鐘。

因此：

- **正式同步流程不建議做截斷重試。**
- 若要保留，只能在「第一次很早失敗且剩餘時間充足」時重試。
- 不能為了重試把 230 秒死線再放大。
- 短規則降級版會少掉使用者驗收過的限制，也會新增凍結 prompt，實作成本不是「只多一個 if」。

### 4. 換模型

#### 推薦備案：`google/gemini-3.8-flash`

OpenRouter 已提供此 ID，支援 JSON Schema structured output。頁面目前顯示約：

- 價格：US$0.75／百萬 input、US$3.75／百萬 output。
- provider 最佳 P50 首 token 延遲約 2 秒。
- 吞吐量可達約 184～202 token/s。
- 有 Google AI Studio 與 Vertex fallback。[OpenRouter Gemini 3.8 Flash](https://openrouter.ai/google/gemini-3.8-flash-20260902)

優點是速度、價格與能力較平衡。風險是模型剛推出不久，且本專案的 prompt 明顯以 Claude 行為調整而成；雖然 schema 很簡單，但真正困難的是二萬字元左右、約束很多的 system prompt，以及臺灣繁中與內容忠實度。

**建議它作為 Sonnet low 失敗後的第一個換模候選。**

#### 極速備案：`google/gemini-3.1-flash-lite`

這是 GA 模型，OpenRouter明確定位為低延遲、高吞吐、簡單資料抽取：

- US$0.25／百萬 input、US$1.50／百萬 output。
- 支援 strict JSON schema。
- thinking 可選 minimal／low／medium／high。
- provider 最佳 P50 約 0.49 秒、117 token/s。[OpenRouter Gemini 3.1 Flash Lite](https://openrouter.ai/google/gemini-3.1-flash-lite)

它在「新聞稿轉 JSON」表面上非常合適，但本專案不是單純欄位抽取：還有版面、點數、忠實度、人物、地圖、繁中與多種檔位規則。Lite 最可能出現的是 JSON 正確、內容卻被品質閘門退回。

因此它應是測試組，不宜未驗證直接取代主模型。

另外，換成 Google 模型時必須讓 provider order 依模型切換；目前白名單是 Anthropic／AWS／Azure／Bedrock，不能原封不動套到 Gemini。

### 5. 降低思考需求

本專案的既有數據已證明「縮短字元但保留相同約束」沒有作用；真正能省的是減少約束數。

可行的長期方向是：

- 明確指定圖表類型時，只注入該類必要規則。
- 將純機械規則移出 prompt，交給 schema、validator 或確定性後處理。
- 不要為每個自動判斷增加一個昂貴分類呼叫；若啟用現成兩階段模式，分類必須是極快的小模型，且總耗時要連同分類一起量。
- 暫時不要刪內容忠實度、繁中、人物與地圖規則；這些都是實際事故留下的防線。

這一條需要逐項重新授權與重凍；[凍結測試](/E:/GitHub/TVBS-AICG-PG/tests/test_reporter_prompt_frozen.py:1) 不能用整批重建掩蓋行為差異。

## 驗證方式與費用

先做完全免費的驗證：

1. 以 mock 確認 Sonnet 5 payload 只送 `effort=low`，不再把 `max_tokens` 當有效保護。
2. 驗證 strict schema、繁中品質閘門、截斷判斷與 provider routing。
3. 用既有 R6 原始輸出重播解析與品質檢查。
4. 補齊 `骗` 這類已知漏網字的測試案例；否則換模型比較會低估簡體問題。

取得付費實測授權後，建議兩段進行：

- **篩選輪：10 次 Sonnet 5 low**，同一篇 2,929 字稿，standard／maximum 各 5 次。
- 通過後再用 **20 篇不同長度、不同角色／版型**驗證，不要只重複同一篇。
- 門檻：
  - `finish=stop` 100%。
  - JSON 解析 100%。
  - 現有品質閘門一次通過至少 95%；30 次樣本最好零截斷。
  - 人工核對繁中、事實忠實度與塊數。
  - 消化時間上限應是 `120 秒 − 生圖 P95 − 安全餘裕`；在還沒有生圖 P95 前，可暫以 **最大 60 秒、P95 45 秒**作篩選門檻。

依 OpenRouter 列價、保守假設每次最多 20K input＋12K output：

- Sonnet 5：約 **US$0.16／次上限**；10 次約 US$1.60，30 次約 US$4.80。
- Gemini 3.8 Flash：約 US$0.06／次；10 次約 US$0.60。
- Gemini 3.1 Flash Lite：約 US$0.023／次；10 次約 US$0.23。

完整「Sonnet low 10 次＋兩支 Gemini 各 10 次＋勝出模型再確認 20 次」的保守上限約 **US$3.6～5.6**，實際通常會更低，因為 low effort 不會吃滿 12K output。

## 兩分鐘的架構判斷

現行「慢模型＋最多五次序列重試＋後續再生圖」無法提供兩分鐘硬保證。串流心跳只能避免 524，不能縮短實際處理時間。

若兩分鐘是整體硬 SLA，架構上至少要有：

- 消化與生圖各自明確的時間配額。
- 依剩餘時間決定是否允許重試；不是固定 `DIGEST_ATTEMPTS=5`。
- 消化超過約 45～60 秒就停止，不能讓單次吃到 120～200 秒。
- 主路徑採低 effort 或 Flash 模型，不能把慢模型失敗後再換快模型當常態。
- 補記消化模型、provider、effort、各階段耗時與失敗原因；否則正式站無法驗證 SLA，這正是 B72／F30／F31 的觀測缺口。
